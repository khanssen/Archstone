Fully reportable

A collector reads the evidence the objective requires, in full. Tenant configuration API and host configuration read carry most of this, at 104 and 95 attributions.

80

Partially reportable

A collector reaches part of what the objective asks for. The remainder needs a person. Partial is not a rounding error toward full — it is its own state, and it is reported as one.

97

Not reached

Of these, 80 have no mechanism assigned at all. They are overwhelmingly definitional — policies defined, roles identified, processes established — which is the honest ceiling on automated evidence, not a backlog.

Methodology

The study was conducted against a fully compliant SP 800-171 Rev 2 enclave built to a single reference architecture: hardened Windows 11, Windows Server 2025 and Ubuntu 24.04 hosts, a Wazuh 4.14 manager, and an Entra/M365 tenant read through the Graph API. Every component is a commonly available building block of enterprise IT. Hardening on the hosts was enforced by script-applied local policy at build time, with Wazuh SCA acting as the drift detector afterward. Each of the 320 assessment objectives in SP 800-171A Rev 2 was evaluated individually, with the objective's determination-statement prose in view rather than its identifier, against a single question: can a collector in the reference architecture read the evidence this objective requires?

The evaluation proceeded in two passes.

  • The first pass used observed hardening data. The reference architecture was scanned, and every configuration check that returned a result was traced to the objective whose prose it satisfies. Those traces are the host-configuration and tenant-configuration attributions, and each was made from an actual scan result.
  • The second pass covered the remaining collector mechanisms running in the same architecture - log collection, file-integrity monitoring, vulnerability detection, system inventory, and active response - and asked, for each objective not already reached, whether the output those mechanisms were producing constitutes the evidence the objective's prose calls for. These mechanisms were deployed and returning data during the study; what distinguishes these attributions from the first pass is that the binding from output to objective was made by examining the data against the determination statement, rather than by a pre-existing scored check.

Each attribution was judged as an assessor would evaluate it: would the evidence this mechanism produces satisfy an examiner reading the determination statement literally, with no inference from adjacent controls and no credit for what the mechanism could be configured to read but is not? Where the answer was yes for part of a statement and no for the rest, the objective was recorded as partial. The evaluation was made from both sides of that exchange - knowing what the mechanism actually emits and what an examiner would accept as evidence of it - which is why partials were not rounded up and why the 80 unreached definitional objectives are recorded as a ceiling rather than a backlog.

Attributions are recorded per mechanism class, not per host, so they carry to any enclave where the same class is deployed, and only to such an enclave. An enclave with no tenant configuration API cannot claim the 104 attributions that class provides here. Conversely, an enclave that deploys a mechanism this architecture does not - an EDR, a DLP engine, a PAM broker - may reach objectives this study records as not reached.
